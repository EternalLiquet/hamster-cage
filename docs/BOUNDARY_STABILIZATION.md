# Office boundary stabilization (#100)

The engine derives attendance from immutable local observations ordered by observation time. It keeps every source ID in the resulting session audit and never rewrites a raw ENTER, EXIT, PRESENCE or ABSENCE. Delivery order and receipt delay do not decide visit order. App-private event evidence retains the source and available observation/receipt times; normal History copy describes office-area observations without showing raw IDs or claiming building entry or exit.

For one office, an EXIT followed by ENTER or PRESENCE within **60 seconds** is treated as a boundary bounce when a visit was already open and no other-office observation occurred between them. The derived visit keeps its original opening and arrival grace. Both observations remain attached to it; the apparent gap earns no second grace window or separate ordinary visit. This is a conservative fixed stabilization window for obvious immediate reversals, not a claim that the person was continuously inside a building. A later return, intervening other-office evidence, or an explicit recovery fix remains a distinct visit. The existing short-gap credit policy never bridges a gap containing other-office evidence or an explicit recovery fix, and never fills the new arrival grace.

Repeated ENTER observations and same-office observations already judged to be routine corroboration do not restart an open visit or create a blocking review. Foreground and periodic background reconciliation append a new PRESENCE only when their capture gate cannot safely treat the old open visit as continuous. Their persisted sources mark those observations for the engine to split the old span as `UNCONFIRMED_GAP` and begin a new fix-time visit; for the old span its credit runs only through the latest same-office current-location fix that placed the user inside, and only up to any later same-office ENTER or other-office observation, which shows the user may have left (an opening ENTER alone earns nothing); the uncertain remainder is uncredited and reviewable. An explicit recovery PRESENCE also takes priority over the 60-second bounce rule after an EXIT. The app passes this recovery marker from persisted event source metadata into the framework-free engine; it is not a mutable attendance fact.

A repeated same-office EXIT with no intervening inside observation is handled by observation time, not delivery time:

- **Within 60 seconds of an unresolved departure EXIT** it is the same departure. Any return between them would be merged by the bounce rule above, so the repeat is retained as a diagnostic of that visit, a following bounce ENTER still continues the visit, and arrival grace is not restarted. If no return follows, credit ends at the first EXIT; the at most 60-second difference is the same jitter tolerance the bounce rule already accepts. If another office has an observation between the two EXITs, the repeat is not absorbed here and is handled as below.
- **After the visit has closed**, a repeat is redundant only while an unobserved return before it could not earn its own credit. A separate visit earns credit only if it lasts longer than both the office's arrival grace and the 60-second transient window. Measured from the visit's closing EXIT, a return in the first 60 seconds would merge, so the bound is `60 s + max(arrival grace, 60 s)`; measured from a later decisive ABSENCE, no merge is possible and the bound is `max(arrival grace, 60 s)`. Both bounds are capped at four minutes, the 60-second bounce window plus the existing three-minute confirmation window beyond which a single observation no longer establishes continuity across an EXIT, so a large arrival grace cannot turn an EXIT hours later into an advisory; a shorter bound only keeps more repeats reviewable. Repeated EXITs never move this anchor because each may itself be the exit of a missed return. Within the bound the visit gains the advisory `REPEATED_EXIT` note: it does not block Today, mark the day for review, or lower confidence below MEDIUM, but it stops short-gap reconciliation after the visit, because a zero-credit hidden visit would block that bridge. If the user actually returned immediately and stayed until the later EXIT, up to four minutes may be missing; the note says so and the visit can be corrected. The engine never over-credits in this case.
- **Beyond the bound**, including an EXIT hours later or on another day, the repeat remains a `MISSING_ENTER` orphan so a possibly missed arrival stays reviewable, and the earlier visit is unchanged.

Repeated EXIT IDs are kept in the session's `redundantEventIds`, never in its source or correction-target IDs. A correction saved against a former orphan session therefore becomes an `ORPHAN_CORRECTION` for review instead of silently rewriting the earlier visit. When the platform supplies no fix time, the stored time is the delivery receipt: a receipt-timed anchor could have been observed much earlier, so it cannot bound the gap and the repeat stays an orphan; a receipt-timed later EXIT was observed no later than stored, so its bound still holds. This rule is office-specific; it does not swallow a different office's evidence. A later ENTER or PRESENCE starts a new visit under the ordinary boundary rules.

An ENTER followed by EXIT within 60 seconds with no continuing earlier visit is one `TRANSIENT_BOUNDARY` review, not a confident departure. It earns no automatic credit; the original evidence remains for an explicit correction. A lone final EXIT beyond the window still ends the derived visit at its observed time. Bounded confirmation (#101) and weekday reconciliation (#89) handle that remaining false-final-exit risk. No continuous location service, exact alarm, upload or new permission is added here.
