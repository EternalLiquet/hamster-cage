# Settings Security Pass (#32)

Scope: policy, calendar and privacy controls (#29–31). New collection, permission, exported component, network endpoint, credential, secret, schema and dependency introduced by this pass: **none**. Existing policy values remain app-private DataStore preferences; calendar exclusions/notes and WFH remain Room facts. The privacy feature's app-private reset journal stores only its version, reset generation, pending flag and retired-geofence cursor. It is not a backup, export or attendance aggregate.

## Boundaries under review

- Form strings become bounded typed policy values before repository writes: nonempty weekdays, valid timezone, target 1–1440 minutes, reconciliation 0–120 minutes and open-session limit 1–24 hours. Invalid stored policy is unavailable and preserved. Device timezone changes cannot silently replace the chosen policy zone. Calendar dates parse strictly and note size is bounded. Existing policy/calendar behavioral tests cover recomputation, stale saves, invalid bytes and sanitized errors.
- Saved calendar notes now receive the same bounded literal display sanitation as history notes. Control/directional characters cannot alter adjacent UI text, while the stored private note remains unchanged. Notes remain intentionally visible in Calendar; screenshots may contain that visible content. No screenshot-prevention claim is made.
- A reset journal is an authorization boundary for destructive recovery. Only an entirely empty journal is initial state. Nonempty partial, wrong-version/type, negative-generation or invalid-cursor metadata must fail unavailable without overwriting bytes or initiating deletion. The security regression checks those cases using real DataStore files, including attempted reset start and actual read denial to shell UID 2000.
- Pending/unavailable reset state hides previously ready attendance and source details across Dashboard, History, Offices and Settings. The UI offers deliberate recovery/full reset, not misleading success or a falsely empty record. The integration additionally pairs reset state with a fresh cold database and coverage subscriptions so a new reset generation cannot reveal cached pre-delete facts or falsely complete coverage.
- History deletion requires an explicit scope preview/confirmation, preserves offices/base policy, and clears the promised attendance/calendar facts and active coverage. Cancel does not write. A persisted pending journal resumes unfinished work; capture and editing share the reset boundary, and obsolete callback generations cannot recreate deleted observations. Old geofence retirement is tracked durably with bounded retries. Full reset uses Android's app-data clearing API and describes request acceptance honestly; the actual process termination/fresh setup probe belongs to #31.
