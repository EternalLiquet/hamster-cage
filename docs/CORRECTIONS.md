# Previewed append-only attendance corrections (#27)

History can add a manual interval or open a session correction from day detail. The editor takes an explicit UTC offset per boundary, so a repeated DST hour is unambiguous. End-before/equal-start, future bounds, sub-millisecond precision, malformed timestamps and oversized notes are rejected. A blank end on a manual interval means explicitly open attendance. A blank end on a session correction changes only the start: the corrected visit keeps the end its own reconstruction observes (bounces merged, the same evidence an uncorrected visit uses) and that end's `UNCONFIRMED_BOUNDARY`/`UNCONFIRMED_GAP` uncertainty. While the reconstruction is still open (including an EXIT still awaiting verification) the corrected visit stays open; once that EXIT settles, it closes. Later visits at this or another office never extend it. An observed end beyond `maxOpenSessionHours` from the corrected start is not trusted: the visit stays open and stale for review, so a departure reported days later cannot credit the gap. Day detail treats such a correction as reaching only as far as the effective visit. The same evidence caps as an uncorrected visit apply (a pending EXIT's cap and `UNCONFIRMED_BOUNDARY`, a rejected EXIT followed by another office, an unconfirmed gap's observed prefix, measured from the later of the corrected start and the visit's first observation); explicit bounds still override them. Moving the start earlier counts toward the open-session limit, so a long visit can become stale. Previously stored blank-end corrections take this meaning too: a visit deliberately held open past a closed phantom EXIT now ends there. To state that you are still present, add a manual interval with a blank end, or set an explicit end after leaving. No raw event is created or changed (#138). Location permission is not required.

Preview runs the shared engine on the proposed immutable facts at a fixed evaluation instant. It displays before/after credited time and requires an explicit confirmation. A shared repository mutex serializes policy saves with confirmed edits. The repository compares all attendance/policy source facts against the preview inside the Room transaction; a new observation or stale edit rejects the confirmation and returns the preserved draft for a fresh preview. Later clock ticks or policy/observation changes can naturally update displayed totals. Success is shown only after commit; failures remain sanitized.

Edits append a correction with MANUAL confidence. Manual intervals have their own source type and never create synthetic geofence ENTER/EXIT events. Repeated edits retain prior audit entries. Reverting appends a `revertToOriginal` marker: the engine restores reconstruction from the retained source facts, including missing boundaries, original confidence and review reasons, with explicit revert audit metadata. The retained correction ID is audit only: candidate, rejected-EXIT/other-office and unconfirmed-gap credit caps, review reasons, Today's estimate and the Dashboard's entered-times tag treat a reverted session exactly like one that was never corrected (`Session.hasActiveCorrection`). A durable positive append sequence makes later valid edits/reverts win even in the same millisecond or with a smaller random ID. Legacy sequence-zero entries retain timestamp/ID ordering. The repository validates the next sequence inside the transaction, and every preview verifies the selected audit ID. Day detail retains all original events and audit entries.

Room schema 2 adds a non-null correction revert flag (default false) and append sequence (default zero), using explicit migration 1→2. Schema 1 files and records remain supported; future/invalid stores preserve data and fail unavailable. There is no destructive migration or source-fact replacement. The marker's existing bounds are retained audit payload and do not define restored attendance.

Checks cover supersession/revert/missing boundary/future or conflicting markers, explicit-offset DST/midnight input, immutable raw facts, preview/final parity, stale/invalid atomic rejection, actual reopen, schema-1 preservation, UI confirmation/failure/restoration and manual provenance. Exact results and independent gates are recorded in the PR. Physical-device checks remain separate.
