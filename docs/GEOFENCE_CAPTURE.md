# Geofence capture contract (#18)

Enabled offices project to Play Services geofences with stable office IDs and their saved circular boundaries. On app launch, return from Settings, permission result, and office edit, the controller reconciles the desired set. It marks registration in progress, removes obsolete boundaries, then adds the current set. A successful `addGeofences` result means registration succeeded; it does **not** prove uninterrupted monitoring, delivered observations, or known current presence. The initial trigger is zero so registering while already inside an office does not manufacture an ENTER. Reboot and longer-term coverage recovery belong to #19.

Draft [#88 PR #91](https://github.com/EternalLiquet/hamster-cage/pull/91) addresses that already-inside gap through a separate, disclosed foreground one-shot check after setup/recovery. With an explicitly requested fresh precise fix whose full accuracy circle lies inside exactly one eligible office, it appends an immutable `FOREGROUND_LOCATION_RECONCILIATION` presence observation at the fix time; it does not fabricate an earlier geofence ENTER or backdate attendance. Arrival grace starts from that observation. An existing open session, repeat check or subsequent Android transition must not create duplicate credit. Outside, overlapping, stale, inaccurate, permission-denied, location-off, timeout, error and cancellation outcomes do not establish a new presence state. The fix's coordinates are not written into the attendance fact or logged. Local tests cover this boundary; independent review, hosted checks and physical behavior remain open.

The registration PendingIntent names one non-exported receiver in this package. [GeofencingClient requires a mutable PendingIntent on Android 12+](https://developers.google.com/android/reference/com/google/android/gms/location/GeofencingClient), so mutability is limited to this explicit broadcast; it does not expose an Activity, service or provider. The receiver accepts only the expected action, a successful Play Services payload, ENTER or EXIT, and nonempty bounded request IDs. A batch of triggering offices commits atomically through Room, including valid delayed delivery after an office is disabled. Unknown offices and malformed deliveries leave source facts unchanged. No coordinates or payloads are logged or stored with the transition.

The receiver records both receipt time and the triggering location's timestamp when the latter is valid and no later than receipt. Without that platform timestamp, event time is the honest receipt time. The raw ID hashes office ID, transition and event time. Identical replay with a later receipt preserves the original source fact and first receipt; a conflicting raw fact under the same ID still fails. The local engine recomputes interval union, so overlapping offices never double credit. A process-restarted shell reads a sanitized delivery-failure flag from app-private DataStore; registration and delivery failures have visible notices without exception details.

History deletion advances a durable capture generation before clearing facts. The callback action identifies that generation; queued callbacks from older generations are rejected even if their fix time is unknown. The full callback check, Room insert and coverage update share the deletion gate with registration reconciliation and editor writes. Prior-generation PendingIntents are retired with a bounded durable cursor so failed removal can be retried after restart without retiring the current fence. If a callback times out behind reconciliation, the durable delivery failure marks an unknown coverage gap rather than healthy presence. These guards were merged with privacy controls #31; they do not prove that Android delivered a transition.

The repository uses `play-services-location:21.3.0` because 21.4.0 currently carries Kotlin 2.3 metadata incompatible with this project's Kotlin 2.1.20 compiler. The newer artifact failed during `:app:kspDebugKotlin`; this is a toolchain compatibility constraint, not a geofencing API change.

Remaining evidence: actual platform transition delivery while the app UI is closed, delayed/background behavior on a physical phone, permission revocation, reboot/force-stop recovery, and manufacturer battery behavior. #19 must establish a recovery/observation boundary before a past EXIT or open session can be used to confirm current presence. #20 audits the complete capture/recovery component and permission surface. Until then dashboard tracking readiness stays conservative and history coverage remains unknown.

Local Pixel 10 Pro XL emulator (API 37) evidence: two isolated Room capture cases pass (multi-office union/replay/unknown-office atomicity and receipt-time fallback); two UI cases pass (sanitized failures and truthful registration wording). An opt-in Play Services probe successfully registered and removed one synthetic 150-meter boundary. This proves the platform accepted the registration and removal requests on that emulator, not that a background transition was delivered. The probe temporarily grants location permissions; a host runner must restore them after instrumentation when it keeps the app installed. Gradle's connected runner in this local run uninstalled the preview package at completion, so no permission grant or preview fixture remained installed.

A later [actual API37 Play Services movement attempt](https://github.com/EternalLiquet/hamster-cage/issues/18#issuecomment-5809758955) ran against two synthetic offices with registration ACTIVE and HOME as the top Activity. Emulator GPS moves yielded no raw Room transition. The provider's last location stayed stale and its GPS request was OFF, so this result is **inconclusive** for app delivery and establishes neither a product defect nor UI-closed/physical-phone acceptance. No transition payload or raw fact was injected. Permissions were restored to denied and the synthetic fact store stayed empty.
